# 预筛加速使用说明

预筛加速由 `AGENT_MOSS_ACCEL` 控制，默认 `0`（关闭），只有设为 `1` 才启用。关闭时全部规则由 Python 检查，不加载加速包，也不需要安装原生加速库。单独配置包路径或库路径不会开启加速。

## 准备原生加速库（生成 `.so`）

启用加速前需要准备原生动态库。AgentMoss 安装包不附带 Hyperscan / Ultrascan，也不会自动下载或编译它们。下面先准备 `.so`；开启加速后，AgentMoss 在后台自动生成规则包。也可以提前手动生成。规则包不包含 `.so`。

当前接入支持 Linux x86_64 和 aarch64。按部署平台选择下面一种构建方式，在目标机器或与它兼容的构建机上执行。示例固定使用 Hyperscan 5.4.2 和 Ultrascan 5.8.0；这两个库版本已有本 PR 的功能验证记录，下面的依赖安装和源码构建命令仍需在实际构建环境执行验证。

两种库都需要开启 `-DBUILD_SHARED_LIBS=ON`。默认构建的 `.a` 静态库不能直接供当前 Python 加载器使用。构建后得到：

| 文件 | 用途 |
| --- | --- |
| `libhs.so.<版本>` | 完整库，支持编译规则和运行扫描；构建规则包时必须使用它 |
| `libhs_runtime.so.<版本>` | 纯运行库，只支持加载已编译的规则数据库和扫描；运行服务时可选用它 |

Ultrascan 也使用 `libhs` 文件名，通过 `AGENT_MOSS_ACCEL_BACKEND=ultrascan` 区分后端。不能把纯运行库用于 `accel build-db`。

### x86_64：编译 Hyperscan 5.4.2

依赖为 C/C++ 编译器、Make、CMake、Python 3、Ragel 6.x（6.9 或 6.10）和 Boost 头文件（至少 1.57）。下面以 Ubuntu 22.04 的软件源为例；其他发行版按其软件包名称安装。示例使用 CMake 3.15～3.x，旧版工程在 CMake 4 上可能因已移除的兼容策略而配置失败。

```sh
sudo apt-get update
sudo apt-get install -y build-essential cmake git python3 ragel libboost-dev pkg-config file

mkdir -p "$HOME/agentmoss-native"
cd "$HOME/agentmoss-native"
git clone --branch v5.4.2 --depth 1 https://github.com/intel/hyperscan.git hyperscan-5.4.2
cd hyperscan-5.4.2

cmake -S . -B build-shared \
  -DCMAKE_BUILD_TYPE=Release \
  -DBUILD_SHARED_LIBS=ON \
  -DPYTHON_EXECUTABLE="$(command -v python3)"
cmake --build build-shared --target hs_shared hs_runtime_shared --parallel 2

export AGENT_MOSS_ACCEL_LIB="$PWD/build-shared/lib/libhs.so.5.4.2"
export AGENT_MOSS_ACCEL_BACKEND=hyperscan
```

这里仅构建两个动态库，不构建可选的测试和性能工具。Boost 只需头文件，不需要编译整个 Boost；这些库目标不要求安装 PCRE、SQLite 或 libpcap。更多构建选项见 [Hyperscan 官方构建说明](https://intel.github.io/hyperscan/dev-reference/getting_started.html)。

### 鲲鹏 aarch64：编译 Ultrascan 5.8.0

在鲲鹏 ARM Linux 环境执行，依赖为 GCC/G++ 10.3 及以上、Make、CMake 3.15～3.x、Python 3、Ragel 6.9 / 6.10 和 Boost 头文件（至少 1.57）。下面以 openEuler 软件源为例；上游安装指南列出的环境为 openEuler 22.03 LTS SP4 / 24.03 LTS SP3。

```sh
sudo yum install -y gcc gcc-c++ make cmake git python3 ragel boost-devel pkgconf-pkg-config file

mkdir -p "$HOME/agentmoss-native"
cd "$HOME/agentmoss-native"
git clone --branch Ultrascan-v5.8.0 --depth 1 https://gitcode.com/boostkit/Ultrascan.git ultrascan-5.8.0
cd ultrascan-5.8.0

cmake -S . -B build-shared \
  -DCMAKE_BUILD_TYPE=Release \
  -DBUILD_SHARED_LIBS=ON \
  -DPYTHON_EXECUTABLE="$(command -v python3)"
cmake --build build-shared --target hs_shared hs_runtime_shared --parallel 2

export AGENT_MOSS_ACCEL_LIB="$PWD/build-shared/lib/libhs.so.5.8.0"
export AGENT_MOSS_ACCEL_BACKEND=ultrascan
```

如果软件源没有 Ragel 或 Boost 版本不满足要求，按 [Ultrascan 官方安装指南](https://gitcode.com/boostkit/Ultrascan/blob/Ultrascan-v5.8.0/docs/zh/installation_guide.md)准备 Ragel 6.10 和 Boost 头文件后，再执行 CMake。Boost 不在系统目录时，可在配置命令中追加 `-DBOOST_ROOT=/实际路径/boost_1_87_0`。这两个库目标不需要上游指南中用于额外工具的 PCRE / SQLite。

以上构建保留在用户目录，无需执行 `sudo make install`。`--parallel 2` 限制为两个编译任务，可以按构建机内存调整；若编译进程因内存不足被终止，改为 `--parallel 1` 后重试。

### 检查库文件和加载结果

先检查文件架构及系统依赖：

```sh
file "$AGENT_MOSS_ACCEL_LIB"
ldd "$AGENT_MOSS_ACCEL_LIB"
```

`file` 输出应与运行机器的 `uname -m` 对应，`ldd` 输出不应出现 `not found`。如果库文件存在但仍无法加载，应先补齐它依赖的系统库；仅设置 `AGENT_MOSS_ACCEL_LIB` 不会自动解决其他动态库依赖。

接着进入已安装本 PR 版本 AgentMoss 的 Python 环境执行：

```sh
python - <<'PY'
import json
from agent_moss.engine.prefilter_native import NativeLibrary

info = NativeLibrary(None).info()
print(json.dumps(info, ensure_ascii=False, indent=2))
assert info['runtime_available'] and info['valid_platform_status'] == 0
assert info['compiler_available'], '构建规则包需要完整的 libhs，当前库缺少编译接口'
PY
```

该检查确认库可加载、平台检查通过且具有编译接口；实际规则能否完成编译还需执行下一节的 `build-db`。检查纯运行库时，移除最后一条 `compiler_available` 断言，其值为 `false` 属于正常情况。

库可由构建机统一生成后分发，无需每台服务器重新编译。复制时保留实际版本文件；若使用 `libhs.so.5` 等软链接，还需保留其目标文件。目标机器的 CPU 指令集、glibc / libstdc++ 等系统依赖必须兼容；即使都是 x86_64 或 aarch64，也不能只凭架构相同认定可运行，应在目标机重复上述检查。构建完成后记录源码提交（`git rev-parse HEAD`）和库版本，便于后续部署使用同一构建产物。

## 生成规则加速包并启用

服务自动生成规则包需要带编译功能的完整库。机器架构、库类型和完整数字版本必须与包一致，Python 小版本不要求一致。

```sh
# 保留上面配置的 AGENT_MOSS_ACCEL_LIB / AGENT_MOSS_ACCEL_BACKEND。
export AGENT_MOSS_ACCEL=1
export AGENT_MOSS_ACCEL_DB=/data/accel/package
```

`AGENT_MOSS_ACCEL_DB` 指向一个专用的真实目录，不能是软链接。目录可以尚不存在，服务需要有创建和写入权限。首次加载前使用 Python；后台生成并加载成功后自动启用加速。

自动生成默认开启。后台每秒检查有效命令规则，规则稳定至少一秒后开始生成。检查和编译也需要时间，并不保证修改后一秒内完成。只修改说明、风险等级、顺序或重复项，不重新生成。

不同服务使用不同目录；共享目录的工作进程必须使用同一套规则来源、原生库和构建配置。库和包都应在容器内可见，环境变量使用容器内路径。

## 更新和手动生成

控制台或规则文件中的命令规则生效后，后台自动更新同一个目录。新改的规则立即由 Python 检查，未改规则继续使用内存中的旧数据库；新包加载成功后替换内存对象，无需重启服务。原本要求重启才生效的规则来源，仍按原有方式生效。

需要提前生成时，可以执行：

```sh
python -m agent_moss.cli accel build-db --profile linux --out /data/accel/package
python -m agent_moss.cli accel status --db /data/accel/package
```

后台自动生成会覆盖该部署可用的各平台、Agent 和场景命令规则。手动包只覆盖部分规则时，可以先加速对应规则，后台随后按完整有效规则集合更新。

SDK 中只存在于内存的自定义扩展，使用实际扫描器的 `export_accel_rules()` 导出为 JSON，再手动生成：

```sh
export AGENT_MOSS_ACCEL_AUTO_BUILD=0
python -m agent_moss.cli accel build-db --rules-file /data/rules.json --out /data/accel/package
```

`--rules-file` 是完整输入，不会追加默认规则。关闭自动生成后，后台仍会加载手动更新的包。只读部署和只提供 `libhs_runtime.so` 的部署，也应关闭自动生成，并提前准备完整包及 `.package.lock` 文件。

## 包文件和故障处理

目录中保存 `database.bin`、`metadata.json`、`metadata.sha256`、`report.json`、`status.json` 和 `.package.lock`。全部规则由 Python 检查时没有 `database.bin`。不保存历史版本目录。

`status.json` 记录生成中（building）、可加载（ready）或失败（failed）。生成与加载共用文件锁；手动操作遇到占用时会提示稍后重试。检测请求只使用内存，不等待生成或读盘。

生成失败时，已有的内存数据库继续使用。磁盘旧文件可能已被覆盖；如果此时重启服务，会先使用 Python，再自动重建。同一组规则生成失败后默认等 30 秒重试。不同来源的服务不能接管已绑定的包目录。

`accel status` 检查磁盘状态和完整性，不表示服务已加载，也不检查原生库是否能运行。应结合对应进程的 `prefilter activated` 日志确认实际启用；`prefilter generated` 只表示生成完成。

当前包为 schema 4。手动模式可只读加载完整的 schema 3 包；启用自动更新时，应配置一个新的真实目录重新生成。共享同一目录的进程和手动命令需要统一升级。包目录应由可信部署管理，摘要检查文件损坏，不验证发布者身份。

## 关闭与退出

在服务启动环境中设置 `AGENT_MOSS_ACCEL=0` 并重启服务即可关闭。环境变量按进程启动配置生效，在其他终端修改不会影响已运行的服务。删除磁盘包不会关闭已加载的内存数据库；自动模式还会重新生成。

SDK 宿主退出时，先停止接收请求并等待在途请求结束，再调用：

```python
import agent_moss
agent_moss.shutdown_acceleration()
```

该接口可重复调用，最多等待五秒。尚未结束的后台任务继续收尾，写文件期间不会提前释放锁。HTTP worker 已接入启动和停止流程；SDK 后续再次扫描仍可启动加速。

预筛只接入命令正则检查。不能加速的规则仍使用 Python，其他检查功能沿用原流程。开启前应验证实际业务收益。原理见 [设计说明](预筛加速设计.md)，验证范围见 [测试说明](预筛加速测试说明.md)。
